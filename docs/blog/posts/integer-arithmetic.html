Arithmetic and strings through one bytecode path

MirrorVM now converts a small set of CIL method bodies into readable bytecode. The runtime dispatches to CIL-named handlers over one shared stack, and every protected method calls the same object-returning Execute method.

The VM has one Stack<object>. Load instructions push values with Push. Arithmetic handlers pop their operands with Pop, calculate one result, and push that result. There is no numeric-only stack API. The interpreter reads bytecode IDs and calls handlers from a registry; handler instances are created outside the execution loop.

From C# to MirrorVM bytecode

These small methods are part of the sample:

static int Add(int left, int right)
{
    return left + right;
}

static int Subtract(int left, int right)
{
    return left - right;
}

static int AddThenSubtract(int left, int right, int adjustment)
{
    return left + right - adjustment;
}

static string MyString()
{
    return "Test";
}

For Add, the converter reads the CIL argument loads and add, then emits:

01 00    LoadArgument 0
01 01    LoadArgument 1
10       Add

LoadArgument uses opcode ID 0x01 followed by a one-byte argument index. Each load pushes that argument. Add has ID 0x10, pops right then left, calculates left + right, and pushes one result. The CIL ret is consumed by the converter; the VM program ends when its byte array ends.

Subtract changes the last byte to 0x13 (Sub). The three-argument method becomes:

01 00    LoadArgument 0
01 01    LoadArgument 1
10       Add
01 02    LoadArgument 2
13       Sub

For (40 + 4) - 2, the stack evolves as [40], [40, 4], [44], [44, 2], then [42]. Each arithmetic handler leaves its own output on that same stack.

String values use the same return path

MyString compiles to CIL ldstr "Test" followed by ret. The converter stores UTF-8 as a four-byte little-endian byte count followed by those bytes:

03                Ldstr opcode ID
04 00 00 00       UTF-8 byte count: 4
54 65 73 74       UTF-8 bytes: "Test"

Ldstr pushes the decoded string. VirtualMachine.Execute(byte[], object[]) returns the one value left on the stack as object. A rewritten string method casts that object back to string; an Int32 or UInt32 method unboxes the I4 result. This is one runtime entrypoint for all supported result types.

For integer operands, the opcode selects signed or unsigned behavior. The runtime arithmetic helper accepts normalized I4 and I8 values, native integers at process pointer width, float, double, and a documented decimal extension. Tests also cover smaller integral types, bool, char, enums, and uint/ulong bit patterns through the same bytecode interpreter.

That runtime test coverage is broader than the method converter. The converter currently accepts only Int32, UInt32, and String parameters and return types. It does not yet virtualize methods whose signatures use Int64, floating-point, or native integer values. This is a first protected slice, not complete CLR numeric emulation.

How the helper compares with HexVM's NumericHelper

MirrorVM's NumericArithmetic is an independent, focused helper, not a copy or drop-in replacement for HexVM's NumericHelper. For this milestone it normalizes small signed/unsigned values, booleans, characters, enums, 32-bit and 64-bit integers, native integers, floating-point values, and the explicit decimal extension. It implements the arithmetic handlers listed above, including checked and unsigned integer forms.

The helper's operation surface is narrower than a general numeric utility: it does not provide comparison, truthiness, bitwise, shift, or general conversion opcode families. It also does not cover Half, Int128, UInt128, BigInteger, or every legal CLI stack pairing. Its tests verify the implemented slice; they do not prove complete CLR compliance.

Unsupported opcodes leave the method unchanged

The sample includes a branch method and a method that calls Add. Branches and Call are not implemented in this VM version, so the converter reports UnsupportedBranch — contains unsupported CIL opcode 'ble.s' and UnsupportedCall — contains unsupported CIL opcode 'call'. It leaves those method bodies as they were. The supported arithmetic and string methods are still converted.

Verified in this milestone

The Release CLI converted five sample methods and reported three skipped methods. The protected sample printed 42, 42, 42, 42, and Test on .NET Framework 2.0, Framework 4.8.1, .NET Core 3.1, and .NET 9. All 13 automated test cases passed on .NET 9.

Stable opcode IDs and visible stack effects make the execution path straightforward to inspect and emulate. That supports reverse engineering and defensive research. It is not a guarantee that every downstream use is benign.
