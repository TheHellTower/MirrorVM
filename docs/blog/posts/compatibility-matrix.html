Compatibility27 September 2026

Compatibility is a target matrix, not a checkbox

MirrorVM's goal spans .NET Framework 2.0 through 4.8.1 and modern .NET. The runtime now builds for .NET Framework 2.0, .NET Standard 2.0, and .NET 9; these build targets and a few verified runs are evidence, not proof of every release in between.

One framework target does not cover every consumer. The runtime includes a net20 build for the oldest CLR surface, a netstandard2.0 build for .NET Core and newer Framework consumers, and a net9.0 build for the current runtime. The virtualizer itself targets .NET 9 to match the Visual Studio baseline for this project.

Builds and runs answer different questions

The runtime builds for all three targets. The protected sample also demonstrates the actual rewrite: its supported arithmetic and string methods call the generic runtime entrypoint, and each output prints 42, 42, 42, 42, then Test. The same protected sample was run on Framework 2.0, Framework 4.8.1, Core 3.1, and .NET 9.

Those checks cover the oldest Framework endpoint and the current Framework endpoint. They do not establish behavior on every intermediate Framework release. Framework versions from 2.0 through 4.8.1 remain the project goal; the current runtime targets provide candidate compatibility paths that still need broader runtime testing.

Current verification boundary

The Release solution build and all 13 automated tests target .NET 9. The protected sample ran on Framework 2.0 and 4.8.1, Core 3.1, and .NET 9. Core 3.1 is out of support and appears only as a compatibility checkpoint. .NET 10 is not a project target because this Visual Studio setup uses .NET 9; no .NET 10 runtime claim is made here.

Why the old target is separate

.NET Standard 2.0 does not cover Framework 2.0, so the runtime is also compiled against the older framework surface. The virtualizer bundles that net20 runtime beside a protected output when one is not already present. The protected methods use ordinary arrays, boxing, and a call to Execute(byte[], object[]), keeping their rewritten stubs simple enough for the old target.

For Framework 4.6.1 and later, .NET Standard 2.0 is the intended shared library path. Microsoft's documentation notes that .NET Framework 4.6.1 has known .NET Standard consumption issues and recommends 4.7.2 or later. See Microsoft's .NET Standard support matrix and the .NET Framework porting overview.

Keep the compatibility claim narrow

The shared runtime source currently uses APIs available in .NET Framework 2.0, but each new feature can add differences in reflection, encoding, numeric conversions, exception behavior, or IL verification. The converter also intentionally supports only a small method-body subset. A method containing an unsupported opcode is left unchanged and reported; an application may therefore contain both virtualized and ordinary methods.
