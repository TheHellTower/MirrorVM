Compatibility is a target matrix, not a checkbox

MirrorVM's compatibility goal spans .NET Framework 2.0 through 4.8.1 and modern .NET through 10. The protected sample and numeric CLR comparisons passed the configured matrix; Framework 4.x uses the installed in-place 4.8.1 CLR.

The runtime builds for net20, netstandard2.0, and net9.0. The virtualizer and unit tests target .NET 9. The sample builds for 25 configured target frameworks. The matrix runner has 26 entries because Framework 3.0 uses the same net20 sample on the CLR 2.0 line.

Builds and runs answer different questions

Each matrix run protects the sample, executes its rewritten arithmetic, string, and numeric methods, and runs a DynamicMethod CLR comparison for every implemented numeric opcode. Any difference in result or exception stops the sample. All 26 configured entries passed at both pointer widths, for 52 protected sample runs.

Framework 4.x uses the machine's .NET Framework 4.8.1 in-place CLR, so those runs verify target-specific sample builds under that runtime, not the behavior of each historical 4.x runtime installed separately. The Framework 3.0 entry reuses the Framework 2.0 sample because the old SDK has no separate 3.0 reference pack.

Verified scope

The Release solution builds 25 configured sample targets. The 26-entry protected sample matrix passed in x86 and x64 processes, from Framework 2.0 through 4.8.1, Core 2.0 through 3.1, and .NET 5 through 10. All 17 unit tests pass on the .NET 9 x64 host. Framework 4.x execution uses the installed 4.8.1 in-place CLR.

This matrix verifies behavior for the current sample and implemented numeric comparisons; it is not a performance benchmark. The dispatch, stack, and decode changes are described in Reducing repeated work in the interpreter, with timing results scoped to that post's workload.

Why the old target is separate

.NET Standard 2.0 does not cover Framework 2.0, so the runtime is also compiled against the older framework surface. The virtualizer bundles that net20 runtime beside a protected output when one is not already present. The protected methods use ordinary arrays and a call to the shared Execute(VirtualMachineProgram, object[]) entrypoint, keeping their rewritten stubs compatible with the old target.

For Framework 4.6.1 and later, .NET Standard 2.0 is the intended shared library path. Microsoft's documentation notes that .NET Framework 4.6.1 has known .NET Standard consumption issues and recommends 4.7.2 or later. See Microsoft's .NET Standard support matrix and the .NET Framework porting overview.

Keep the compatibility claim narrow

The matrix is evidence for the implemented linear method subset and the numeric cases in the sample; it does not establish full CLR compatibility. The converter does not yet support locals, branches, calls, fields, arrays, byrefs, pointers, or exception regions. A method containing an unsupported opcode is left unchanged and reported, so an application may contain both virtualized and ordinary methods.
