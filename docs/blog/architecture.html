How MirrorVM executes a protected method

A supported CIL body becomes bytecode. A rewritten method stub sends that bytecode and its arguments through one VM entrypoint. Opcode handlers perform the work on one stack.

The execution path

Assembly method body
        ↓
MethodBodyConverter ── unsupported? ── keep original CIL and report why
        ↓ supported CIL
Serialized MirrorVM bytecode
        ↓
Rewritten method stub: bytecode + object[] arguments
        ↓
VirtualMachine.Execute(byte[], object[])
        ↓
One Stack<object> ← registered IOpCode handlers
        ↓
object result → cast/unbox in the rewritten method

Conversion decides for the whole method

The converter reads a method's signature and instructions. It emits bytecode only when the entire body fits the implemented subset. A call, branch, local, exception region, or unsupported signature makes the converter keep the original method body and report the reason. It does not replace only part of a method.

The virtualizer writes a small stub for a converted method. The stub creates the bytecode array and an object[] for arguments, calls the same Execute(byte[], object[]) method for every supported return type, then casts or unboxes the returned object to the declared type.

Bytecode dispatch stays explicit

Execute reads one opcode ID at a time and looks up its registered IOpCode handler. The handler reads any operands, pops inputs, performs its operation, and pushes its result when the opcode produces one. There is one VM stack and one pair of stack operations; arithmetic does not use a separate numeric stack.

This keeps the correspondence between bytecode and behavior visible. A reader can follow an instruction to its handler and inspect the stack effect. The structure is intended to make protected code easier to study for reverse engineering and defensive research.

Why the stack is not the full CLR value model yet

The current Stack<object> represents the values in the implemented subset, including boxed integers and floating-point values, strings, native integers, and by-value Decimal. It does not yet represent managed byrefs, pointers, function pointers, typed references, or arbitrary value-type storage. Those values cannot all be treated as ordinary boxed objects: their lifetime, aliasing, layout, and GC behavior are part of CLR semantics.

As support grows, those representations must still fit the VM's single operand stack and shared execution path. The converter must also validate stack types, control flow, calls, prefixes, and exception regions before claiming broader compatibility.

The current numeric instruction set and representative C#-to-bytecode examples are described in M2 - Numeric values end to end.

Current implementation boundary

The converter handles linear arithmetic and string methods plus the implemented numeric arithmetic, comparison, bitwise, shift, ckfinite, and conv.* instructions. Calls, branches, fields, arrays, object signatures, and exception handling remain unsupported. See the current limits and runtime evidence.
